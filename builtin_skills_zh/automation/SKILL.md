# 定时自动化任务 (Scheduled Automations)

**定时自动化** 是指一种后台 Sidecar 进程 (`"builtin": "schedule"`)，它按照 Cron 表达式定时执行，并在每次运行时启动一个全新的智能体独立会话 (`agentapi new-conversation`)。

本技能**严格专用于定时 (Cron) 自动化任务**。请勿使用它来创建 UI 辅助容器、持续运行的通用命令行/守护进程容器或会话内单次定时器（会话内定时请使用 `schedule` 工具）。

## 快速上手 (5 步交互式创建流程)

1.  **第 1 轮 — 确认执行周期**：通过 `ask_question` 询问（`每小时`、`每天`、`每周` 或 `自定义 Cron 表达式`）。
2.  **第 2 轮 — 确认具体时间 / 日期**：通过 `ask_question` 确认具体的执行时间或星期几。
3.  **第 3 轮 — 明确任务 Prompt**：询问智能体每次运行时应执行什么任务，并精炼为自包含的高质量提示词。
4.  **第 4 轮 — 写入 `sidecar.json`**：在 `<configDir>/sidecars/<slug>/sidecar.json` 中创建配置，设置 `"builtin": "schedule"`, `"args": [...]`。
5.  **第 5 轮 — 可选测试运行**：主动提议立即执行一次测试运行，以精准配置所需的权限白名单。

## 交互式创建工作流

引导用户**分步骤**逐轮完成自动化的设计。如果用户在最初的提问中已经提供了部分细节（如时间或具体任务），请跳过已明确的步骤，直接推进到尚未确定的环节。

### 第 1 轮：询问执行频度

若频度尚未指定，请使用 `ask_question` 工具提问：

-   **问题 (Question)**：`"该自动化的执行周期应当是怎样的？"`
-   **选项 (Options)**：
    -   `每天`
    -   `每周`
    -   `每小时`
    -   `自定义 Cron 表达式`

等待用户回复后再进行下一步。

### 第 2 轮：确认具体时间 / 星期

根据选定的频度，在下一轮中使用 `ask_question` 确认精确时间：

-   **若为每天**：使用 `ask_question` 确认每天的具体时刻（例如：`9:00 AM`、`12:00 PM`、`5:00 PM`；用户亦可通过自定义输入填写）。
-   **若为每周**：使用 `ask_question` 确认每周的哪几天（例如：`周一`、`周五`、`工作日 (周一至周五)`）以及具体时刻。
-   **若为每小时**：默认为每小时整点 (`0 * * * *`)，或确认是否有特定分钟偏移需求。
-   **若为自定义 Cron**：请用户提供所需的 5 位 Cron 表达式（例如：`*/30 * * * *` 表示每 30 分钟一次）。

等待用户确认后再推进至任务定义。

### 第 3 轮：明确智能体需要执行的任务

在时间安排确定后（且任务内容尚未详述时），以纯文本形式直接向用户提问（此开放式步骤**不要**使用 `ask_question`）：

> *“您希望该自动化任务具体执行什么内容？（例如：‘总结过去 24 小时内的未读邮件，并高亮需要回复的邮件’，或者‘检查代码库中的开放 Pull Request 并汇总检查失败的项’）”*

等待用户回复具体需求。

## 第 4 步：创建 `sidecar.json` 并提议测试运行以配置权限

### 1. 转换 Cron 表达式并编写自包含运行 Prompt

-   **Cron 时间表**：标准 5 位 Cron 表达式 (`分 时 日 月 星期`)，基于用户本地时间编写，始终带上 `CRON_TZ=<IANA 时区>` 前缀以确保按用户时区执行：
    -   每小时整点：`CRON_TZ=Asia/Shanghai 0 * * * *`
    -   每天上午 9:00：`CRON_TZ=Asia/Shanghai 0 9 * * *`
    -   每天下午 5:00：`CRON_TZ=Asia/Shanghai 0 17 * * *`
    -   每周一上午 9:00：`CRON_TZ=Asia/Shanghai 0 9 * * 1`
    -   工作日上午 9:00：`CRON_TZ=Asia/Shanghai 0 9 * * 1-5`
-   **确定用户时区**（标准 IANA 时区名称，例如 `Asia/Shanghai` 或 `Europe/Zurich`；严禁使用类似 `CST`、`PST` 等简写或 `+08:00` 偏移）：
    1.  如果用户已明确指定城市或时区，直接转换为对应 IANA 名称；
    2.  否则检测宿主机的系统时区映射为 IANA 时区；
    3.  若检测失败，使用 `ask_question` 请用户确认；
    4.  若用户提供了已自带 `CRON_TZ=` 或 `TZ=` 的 Cron 字符串，原样保留，不要重复添加前缀；
    5.  向用户确认时间安排时，明确带上时区信息（例如：“北京时间每天上午 9:00”）。
-   **自包含提示词 (Self-contained Prompt)**：每次定时启动都是一个全新的独立会话，没有任何前置记忆。请编写清晰、完整的提示词，指明数据源、具体操作步骤以及期望的输出格式。

### 2. 告知用户并写入 `<configDir>/sidecars/<sidecar-id>/sidecar.json`

在调用文件写入工具前，**始终先输出一句简短消息告知用户**：正在创建 **`<display_name>`** 自动化任务。

配置文件路径：
```
<configDir>/sidecars/<sidecar-id>/sidecar.json
```

-   `<configDir>` 是用户的全局配置目录（通常为 `~/.gemini/config`）。
-   `<sidecar-id>` 是基于任务英文命名的短标识符（`kebab-case`，如 `daily-pr-check`）。
-   指定清晰易懂的 **`display_name`**（例如：`"每日 PR 状态检查"`）。在引导用户前往自动化仪表盘时，必须告知此确切名称。
-   字段名严格使用 **snake_case**（如 `restart_policy`, `display_name`, `agent_permissions`, `access_grants`, `workspace_uris`）。
-   `restart_policy` 必须为小写字符串（`"builtin": "schedule"` 必须为 `"always"`）。

> [!CAUTION] **严禁臆测不存在的权限或工具**：
> - 绝对不要凭空捏造未确认存在的 MCP 工具 (`mcp(...)`) 或命令行工具 (`command(...)`)；
> - 只有在当前环境确实存在的工具才允许加入授权；
> - 严禁使用泛化的全局通配符（如 `command(*)`, `read_file(*)`, `write_file(*)`, `mcp(*)`）。

#### `sidecar.json` 示例

```json
{
  "builtin": "schedule",
  "args": [
    "CRON_TZ=Asia/Shanghai 0 9 * * *",
    "agentapi",
    "new-conversation",
    "--",
    "检查代码库中当前开放的 Pull Request，汇总测试失败或有待处理评审意见的 PR 列表。"
  ],
  "restart_policy": "always",
  "display_name": "每日 PR 状态检查",
  "description": "每天上午 9:00（Asia/Shanghai），自动检查开放的 PR 并总结未通过的检查或评审意见。",
  "agent_permissions": {
    "access_grants": [
      "command(gh pr list)",
      "command(gh pr view)"
    ]
  }
}
```

-   `args[0]` **必须**是包含 `CRON_TZ=<zone>` 前缀的完整 Cron 字符串；
-   在 `args` 中的提示词前紧跟 `"--"`，以便将 Prompt 与 `agentapi new-conversation` 的参数彻底分隔。

### 3. 指引用户前往仪表板并提议预跑以配置权限

> [!CAUTION] **切勿自行启用该自动化**。绝对不要擅自修改 `user_config.json` 将 `"enabled": true`，亦不要调用后台 RPC 直接启动它。

在写入 `sidecar.json` 后：

1.  告知用户自动化 **`<display_name>`** (`<sidecar-id>`) 已创建完成，并指引用户点击链接前往**自动化仪表盘**开启：`[打开自动化仪表盘](sidecar://dashboard)`；
2.  向用户解释：**开启后，该任务将在独立项目中无人值守运行，所有未预先授权的命令都会被系统自动拒绝**。为了让任务能够顺畅无阻地运行，建议现在立即执行一次测试运行以自动配置准确的权限白名单。
3.  使用 `ask_question` 询问用户是否立即执行测试运行：
    -   **问题 (Question)**：`"启用后，'<display_name>' 将在继承全局权限的项目中无人值守运行，未被批准的命令将被自动拦截。您希望我现在执行一次测试运行以配置好相应权限吗？"`
    -   **选项 (Options)**：
        -   `(推荐) 是的，现在执行测试运行以配置权限`
        -   `不用了，我稍后直接在自动化仪表板中查看并开启`

## 第 5 步：如果用户选择现在测试运行

当用户同意测试运行时：

1.  **在当前会话中执行一次完整任务**：
    -   检索相关技能或验证所需的 MCP 工具；
    -   执行实际的命令、文件读写、URL 访问或工具调用；
    -   若发现缺失某项环境依赖或需要授权，明确告知用户。
2.  **根据实际调用的工具更新 `sidecar.json` 中的权限**：
    -   将测试运行中实际使用到的操作精炼地录入到 `agent_permissions`：
        -   **`workspace_uris`**：需要读写工作区目录时配置 `["file:///绝对路径"]`；
        -   **`access_grants`**：如 `command(gh pr list)`、`read_file(...)`、`write_file(...)`、`mcp(...)` 等。
3.  **最终确认**：
    -   向用户汇报已补充的权限白名单，并提醒用户在**自动化仪表盘**中开启：`[打开自动化仪表盘](sidecar://dashboard)`。
